01

Classic 3-Tier Web ApplicationKlasszikus 3-rétegű webalkalmazás

SolvesMit old megserving a normal website reliably to many users, with the database protected deep inside and no single machine being a point of failure.egy normál weboldal megbízható kiszolgálása sok felhasználónak, az adatbázissal mélyen, védetten belül, és úgy, hogy egyetlen gép se legyen hibapont.
Made ofMiből állthree tiers, each in its own subnet: a web tier (serves the frontend) → an app tier (API and business logic) → a database. A load balancer in front spreads traffic, and every tier is duplicated across two Availability Zones.három réteg, mindegyik saját subnetben: egy webréteg (a frontendet szolgálja) → egy app-réteg (API és üzleti logika) → egy adatbázis. Egy load balancer elöl szétosztja a forgalmat, és minden réteg két Availability Zone-ban duplikálva van.

The reference architecture almost every interview starts from. Three tiers — web, application, data — each in its own subnet, spread across two Availability Zones for high availability. The load balancer sends the user to the web tier (which serves the frontend); the web tier calls the app tier (the API and business logic); the app tier talks to the database. Each tier only accepts traffic from the one in front of it — the security groups enforce that chain.A referencia-architektúra, amiből szinte minden interjú indul. Három réteg — web, alkalmazás, adat — mindegyik a saját subnetjében, két Availability Zone között szétosztva a magas rendelkezésre állásért. A load balancer a webréteghez küldi a felhasználót (ami a frontendet szolgálja); a webréteg hívja az app-réteget (az API és üzleti logika); az app-réteg beszél az adatbázissal. Minden réteg csak az előtte lévőtől fogad forgalmat — a security groupok kényszerítik ki ezt a láncot.

Key settings — the security group chainKulcs-beállítások — a security group lánc

  • sg-albinbound 443 from 0.0.0.0/0 (the internet). The load balancer is the only thing open to the world.bejövő 443 innen: 0.0.0.0/0 (az internet). A load balancer az egyetlen, ami nyitott a világ felé.
  • sg-webinbound 80 from sg-alb only — the web tier is reachable only through the load balancer, not directly from the internet.bejövő 80 csak sg-alb-ből — a webréteg csak a load balanceren át érhető el, nem közvetlenül az internetről.
  • sg-appinbound 8080 from sg-web only — the app tier trusts only the web tier's security group, by reference, not an IP range.bejövő 8080 csak sg-web-ből — az app-réteg csak a webréteg security groupjában bízik, hivatkozással, nem IP-tartománnyal.
  • sg-dbinbound 5432 from sg-app only. The database accepts connections from the app tier and nothing else — no public path exists to it at all.bejövő 5432 csak sg-app-ből. Az adatbázis az app-rétegből fogad kapcsolatot és semmi másból — egyáltalán nincs publikus út hozzá.
  • NACLthe data subnet's NACL can add a coarse backstop (e.g. deny all inbound except the app subnet's CIDR on 5432) — a second, stateless layer beneath the SGs.a data subnet NACL-je hozzáadhat egy durva tartalékot (pl. minden bejövő tiltása az app subnet CIDR-jén kívül a 5432-n) — egy második, állapotmentes réteg az SG-k alatt.

Why this shapeMiért ez a formaThe referencing-SG pattern means you never hardcode IPs, and the chain (internet → ALB → app → DB) makes the blast radius of any one compromised tier small. RDS is Multi-AZ: a synchronous standby in the second AZ takes over automatically if the primary's AZ fails. Everything except the ALB lives in private subnets.A referencing-SG minta azt jelenti, hogy sosem kódolsz be IP-ket fixen, és a lánc (internet → ALB → app → DB) kicsivé teszi egy kompromittált réteg blast radiusát. Az RDS Multi-AZ: egy szinkron standby a második AZ-ban automatikusan átveszi, ha a primary AZ-ja elhal. Minden az ALB-n kívül privát subnetekben él.

02

Serverless ApplicationServerless alkalmazás

SolvesMit old megrunning an API or app without managing any servers, paying only when it's actually used — ideal for spiky or unpredictable traffic.egy API vagy app futtatása szerverek kezelése nélkül, csak akkor fizetve, amikor tényleg használják — ideális csúcsos vagy kiszámíthatatlan forgalomhoz.
Made ofMiből állAPI Gateway (the front door) → Lambda functions (the code) → DynamoDB / S3 (storage), with Cognito for login. All managed; no VPC unless a function needs a private database.API Gateway (a bejárat) → Lambda függvények (a kód) → DynamoDB / S3 (tárolás), Cognitóval a bejelentkezéshez. Mind menedzselt; nincs VPC, hacsak egy függvénynek nem kell privát adatbázis.

The same job with almost no infrastructure to manage. There are no subnets or security groups for the core path — API Gateway, Lambda, and DynamoDB are fully managed and scale to zero. A VPC only appears if a function needs to reach a private resource like RDS; then that one Lambda gets a subnet and a security group.Ugyanaz a feladat szinte semmi kezelendő infrastruktúrával. Nincsenek subnetek vagy security groupok a mag-úthoz — az API Gateway, Lambda, és DynamoDB teljesen menedzselt és nullára skálázódnak. Egy VPC csak akkor jelenik meg, ha egy függvénynek el kell érnie egy privát erőforrást, mint az RDS; akkor az az egy Lambda kap egy subnetet és egy security groupot.

Key settings — where control lives without SGsKulcs-beállítások — hol a kontroll SG-k nélkül

  • API Gatewayhandles TLS, throttling, and can require a Cognito token before the request ever reaches a Lambda.kezeli a TLS-t, throttlingot, és megkövetelhet egy Cognito tokent, mielőtt a kérés elérne egy Lambdát.
  • IAM roleeach Lambda has its own execution role scoped to exactly what it needs (e.g. read one DynamoDB table). This replaces network rules as the primary access control.minden Lambdának saját execution role-ja van, pontosan arra szűkítve, amire szüksége van (pl. egy DynamoDB tábla olvasása). Ez helyettesíti a hálózati szabályokat mint elsődleges hozzáférés-vezérlés.
  • sg-fnappears only for the VPC-attached Lambda — inbound is irrelevant (nothing calls it directly); outbound 5432 to sg-db lets it reach RDS.csak a VPC-hez csatolt Lambdánál jelenik meg — a bejövő irreleváns (semmi nem hívja közvetlenül); a kimenő 5432 az sg-db felé engedi elérni az RDS-t.
  • Cognitothe user pool issues tokens; identity enters the request here, so every downstream call can be authorised per user.a user pool tokeneket bocsát ki; az identitás itt lép be a kérésbe, így minden lejjebbi hívás felhasználónként engedélyezhető.

Why this shapeMiért ez a formaWith managed services the security model shifts from network boundaries to IAM: no subnets to defend, but every function's role must be least-privilege. It scales to zero (cheap for spiky load) but watch cold starts on latency-sensitive paths. The VPC-attached Lambda is the exception that proves the rule — you only pay the networking complexity where you actually touch a private resource.A menedzselt szolgáltatásokkal a biztonsági modell a hálózati határokról az IAM-re tolódik: nincs védendő subnet, de minden függvény role-jának legkisebb jogosultságúnak kell lennie. Nullára skálázódik (olcsó csúcsos terheléshez), de figyeld a hidegindítást késleltetés-érzékeny utakon. A VPC-hez csatolt Lambda a kivétel, ami erősíti a szabályt — csak ott fizeted a hálózati bonyolultságot, ahol tényleg egy privát erőforráshoz nyúlsz.

03

Containerised Application (ECS Fargate)Konténerizált alkalmazás (ECS Fargate)

SolvesMit old megrunning a containerised app (packaged, portable) without managing the servers underneath — the middle ground between plain EC2 and fully serverless.egy konténerizált app (csomagolt, hordozható) futtatása az alatta lévő szerverek kezelése nélkül — a középút a sima EC2 és a teljesen serverless között.
Made ofMiből állthe same shape as the 3-tier app — load balancer → app tier → database — but the app tier is Fargate tasks (containers AWS runs for you) instead of EC2 servers.ugyanaz a forma, mint a 3-rétegű appnál — load balancer → app-réteg → adatbázis — de az app-réteg Fargate taskok (konténerek, amiket az AWS futtat neked) EC2-szerverek helyett.

The middle ground: the same 3-tier network shape as the classic web app, but the app tier runs containers as Fargate tasks instead of EC2 instances. You get the portability and packaging of containers without managing the underlying servers — AWS runs the nodes. The network layout, subnets, and security-group chain are identical to the EC2 version.A középút: ugyanaz a 3-rétegű hálózati forma, mint a klasszikus webappnál, de az app-réteg konténereket futtat Fargate taskokként EC2 instance-ok helyett. Megkapod a konténerek hordozhatóságát és csomagolását az alatta lévő szerverek kezelése nélkül — az AWS futtatja a node-okat. A hálózati elrendezés, subnetek, és security-group lánc azonos az EC2-verzióval.

Key settings — same chain, container specificsKulcs-beállítások — ugyanaz a lánc, konténer-specifikumok

  • sg-taskinbound the app port from sg-alb only — same principle as sg-app before. Each Fargate task gets its own elastic network interface in the private subnet.bejövő az app-port csak sg-alb-ből — ugyanaz az elv, mint korábban az sg-app. Minden Fargate task saját elastic network interfészt kap a privát subnetben.
  • task rolethe container's IAM role (like a Lambda's) grants app-level AWS permissions; the separate execution role lets ECS pull the image and write logs.a konténer IAM role-ja (mint egy Lambdáé) app-szintű AWS-jogosultságokat ad; a külön execution role engedi az ECS-nek az image-húzást és a log-írást.
  • ECR + endpointstasks pull the image from ECR. In private subnets, VPC endpoints for ECR and S3 let them pull without a NAT gateway — saving cost and keeping it internal.a taskok az ECR-ből húzzák az image-et. Privát subnetekben az ECR-hez és S3-hoz tartozó VPC endpointok engedik a húzást NAT gateway nélkül — költséget spórolva és belül tartva.
  • scalingECS service auto scaling adds/removes tasks on a metric (CPU, request count) — the container equivalent of an ASG.az ECS service auto scaling taskokat ad/vesz egy metrikán (CPU, kérésszám) — az ASG konténer-megfelelője.

Why this shapeMiért ez a formaFargate keeps the familiar VPC/subnet/SG model — so everything you know about the 3-tier app still applies — while removing node patching and capacity management. ECS (shown) is the simpler AWS-native choice; EKS would look the same at the network level but run Kubernetes. The VPC endpoints for image pulls are the detail that separates a cost-aware design from one quietly paying NAT charges.A Fargate megtartja az ismerős VPC/subnet/SG modellt — tehát minden, amit a 3-rétegű appról tudsz, még érvényes — miközben megszünteti a node-patchelést és kapacitás-kezelést. Az ECS (látható) az egyszerűbb AWS-natív választás; az EKS ugyanígy nézne ki hálózati szinten, de Kubernetest futtatna. Az image-húzáshoz tartozó VPC endpointok a részlet, ami elválasztja a költség-tudatos tervet attól, ami csendben NAT-díjat fizet.

Event-Driven PipelineEseményvezérelt pipeline

SolvesMit old megprocessing a large or bursty flow of events (orders, uploads, sensor data) without any stage overwhelming the next — and without losing events when something fails.egy nagy vagy hullámzó esemény-folyam feldolgozása (rendelések, feltöltések, szenzoradat) anélkül, hogy bármelyik szakasz elárasztaná a következőt — és események elvesztése nélkül, ha valami hibázik.
Made ofMiből állproducers → a queue (SQS) or stream (Kinesis) → consumers (Lambda) → storage (DynamoDB / S3), with a dead-letter queue catching failures. Each stage scales on its own.termelők → egy sor (SQS) vagy stream (Kinesis) → fogyasztók (Lambda) → tárolás (DynamoDB / S3), egy dead-letter queue-val, ami elkapja a hibákat. Minden szakasz külön skálázódik.

A different shape entirely — not request/response but a flow of events through decoupled stages. Producers drop events onto a queue or stream; consumers process them at their own pace; results land in a store. Each stage scales independently, and a slow or failed consumer can't push back on the producer.Egészen más forma — nem kérés/válasz, hanem események folyama szétcsatolt szakaszokon át. A termelők eseményeket dobnak egy sorra vagy streamre; a fogyasztók saját tempójukban dolgozzák fel; az eredmények egy tárolóba érkeznek. Minden szakasz függetlenül skálázódik, és egy lassú vagy hibázó fogyasztó nem tud visszanyomni a termelőre.

Key settings — queue vs stream, and failure handlingKulcs-beállítások — sor vs stream, és hibakezelés

  • SQS vs KinesisSQS = a work queue (each message processed once, then deleted). Kinesis = an ordered, replayable log (multiple consumers, replay history). Choose by whether you need ordering and replay.SQS = munkasor (minden üzenet egyszer feldolgozva, majd törölve). Kinesis = rendezett, visszajátszható log (több fogyasztó, történet-visszajátszás). Aszerint válaszd, kell-e sorrend és visszajátszás.
  • DLQa message that fails repeatedly is moved to a dead-letter queue instead of blocking the queue — you inspect and reprocess it separately.egy ismételten hibázó üzenet egy dead-letter queue-ba kerül, ahelyett hogy blokkolná a sort — külön vizsgálod és újra-feldolgozod.
  • idempotencydelivery is at-least-once, so a message can arrive twice — consumers must be idempotent (processing the same event twice has no extra effect).a kézbesítés at-least-once, tehát egy üzenet kétszer is megérkezhet — a fogyasztóknak idempotensnek kell lenniük (ugyanazon esemény kétszeri feldolgozása nem jár extra hatással).
  • sinksprocessed events land in DynamoDB (fast lookups) and/or an S3 data lake, where Athena can run SQL analytics over the raw history.a feldolgozott események DynamoDB-be (gyors keresés) és/vagy egy S3 data lake-be érkeznek, ahol az Athena SQL-analitikát futtathat a nyers történeten.

Why this shapeMiért ez a formaDecoupling is the whole point: a traffic spike fills the queue instead of overwhelming the database, and each stage scales to its own load. The DLQ and idempotency are what make it robust in practice — without them, one poison message or one duplicate can corrupt the pipeline. This is mostly managed services, so there's little network to secure; IAM roles between stages do the access control.A szétcsatolás a lényeg: egy forgalmi csúcs feltölti a sort, ahelyett hogy elárasztaná az adatbázist, és minden szakasz a saját terheléséhez skálázódik. A DLQ és az idempotencia teszik robusztussá a gyakorlatban — nélkülük egy méreg-üzenet vagy egy duplikátum megronthatja a pipeline-t. Ez főleg menedzselt szolgáltatás, tehát kevés a védendő hálózat; a szakaszok közti IAM role-ok végzik a hozzáférés-vezérlést.

Multi-AZ High Availability + Cross-Region DRMulti-AZ magas rendelkezésre állás + cross-region DR

SolvesMit old megstaying online through failures — from a single data centre dying (cheap, automatic) up to an entire AWS region going down (rare, needs a plan).online maradás hibákon át — egyetlen adatközpont elhalásától (olcsó, automatikus) egészen egy teljes AWS-régió kieséséig (ritka, terv kell hozzá).
Made ofMiből álla primary region running Multi-AZ (auto-failover between data centres) + a warm standby in a second region, with Route 53 switching traffic if the primary dies.egy primary régió Multi-AZ-ban futva (auto-failover adatközpontok között) + egy meleg tartalék egy második régióban, a Route 53 átkapcsolja a forgalmat, ha a primary elhal.

Two different resilience problems, side by side. Multi-AZ (inside the primary region) survives a data-centre failure automatically and cheaply — it's the production baseline. Cross-region DR survives a whole-region outage, which is rarer, costlier, and needs a deliberate strategy. Route 53 failover DNS points at the primary and switches to the DR region if the primary goes dark.Két különböző reziliencia-probléma egymás mellett. A Multi-AZ (a primary régión belül) automatikusan és olcsón túlél egy adatközpont-hibát — ez a produkciós alapvonal. A cross-region DR egy teljes régió kiesését éli túl, ami ritkább, drágább, és szándékos stratégiát igényel. A Route 53 failover DNS a primaryre mutat, és a DR-régióra vált, ha a primary elsötétül.

Key settings — the two layers of resilienceKulcs-beállítások — a reziliencia két rétege

  • Multi-AZ RDSa synchronous standby in a second AZ; automatic failover on primary failure. RPO near-zero, RTO minutes — all within one region.egy szinkron standby egy második AZ-ban; automatikus failover a primary hibájakor. RPO közel nulla, RTO percek — mind egy régión belül.
  • cross-regionan async read replica and S3 cross-region replication (CRR) keep a warm copy in the DR region. Async = a small RPO (some in-flight data can be lost), because it can't be synchronous across that distance.egy async read replika és S3 cross-region replication (CRR) meleg másolatot tart a DR-régióban. Async = kis RPO (némi úton lévő adat elveszhet), mert azon a távon nem lehet szinkron.
  • Route 53failover routing policy with health checks: serves the primary while healthy, flips to DR automatically when it isn't. A low TTL makes the flip fast.failover routing policy health checkekkel: a primaryt szolgálja, míg egészséges, automatikusan a DR-re vált, amikor nem. Egy alacsony TTL gyorssá teszi a váltást.
  • warm standbythe DR region runs scaled-down; on failover you scale it up. Cheaper than active-active, larger RTO. The right point on the cost/speed curve for most systems.a DR-régió kicsinyítve fut; failovernél felskálázod. Olcsóbb, mint az active-active, nagyobb RTO. A legtöbb rendszerhez a helyes pont a költség/sebesség görbén.

Why this shapeMiért ez a formaDon't reach for multi-region reflexively — it multiplies cost and complexity. Multi-AZ covers the overwhelming majority of failures. Add cross-region DR only when the requirement (an RTO/RPO the business signs off on, or a regulatory demand) justifies it, and pick the cheapest DR tier that meets those numbers. And a DR plan you've never failed over to is a hypothesis, not a plan — test it.Ne nyúlj a multi-regionhöz reflexből — megsokszorozza a költséget és bonyolultságot. A Multi-AZ a hibák elsöprő többségét lefedi. Cross-region DR-t csak akkor adj hozzá, ha a követelmény (egy RTO/RPO, amit az üzlet jóváhagy, vagy egy szabályozási igény) indokolja, és a legolcsóbb megfelelő DR-réteget válaszd. És egy DR-terv, amire sosem failoveráltál, egy hipotézis, nem terv — teszteld.

Observability & LoggingObservability & logolás

SolvesMit old megknowing what your system is doing and why — spotting problems, getting paged when users are affected, and being able to investigate after the fact.tudni, mit csinál a rendszered és miért — problémák észlelése, riasztás, amikor a felhasználókat érinti, és utólagos kivizsgálás lehetősége.
Made ofMiből állevery service emits signals → collected by CloudWatch (metrics/logs), X-Ray (traces), CloudTrail (audit) → turned into dashboards, alarms that page on-call, and threat detection.minden szolgáltatás jeleket bocsát ki → a CloudWatch (metrikák/logok), X-Ray (trace-ek), CloudTrail (audit) gyűjti → dashboardokká, on-callt riasztó alarmokká, és fenyegetés-észleléssé alakul.

How signal flows from every part of the system to the people and tools that act on it. Sources on the left emit metrics, logs, and traces; collection services in the middle gather them; dashboards, alarms, and threat detection on the right turn them into action. The three pillars — metrics, traces, logs — answer three different questions.Ahogy a jel minden rendszer-részből az emberekhez és eszközökhöz folyik, amelyek cselekszenek rá. A források balra metrikákat, logokat, és trace-eket bocsátanak ki; a gyűjtő-szolgáltatások középen összeszedik őket; a dashboardok, riasztások, és fenyegetés-észlelés jobbra cselekvéssé alakítják. A három pillér — metrikák, trace-ek, logok — három különböző kérdést válaszol meg.

Key settings — the three pillars and where they goKulcs-beállítások — a három pillér és hova mennek

  • metricsCloudWatch collects them from AWS services automatically. Alarms fire on symptoms users feel — error rate, p95/p99 latency, saturation — not on raw CPU, and page the on-call via SNS.a CloudWatch automatikusan gyűjti őket az AWS-szolgáltatásokból. A riasztások a felhasználók által érzett tünetekre szólnak — hibaarány, p95/p99 késleltetés, telítettség — nem a nyers CPU-ra, és az on-callt riasztják SNS-en át.
  • tracesX-Ray (or OpenTelemetry) follows one request across services, turning "the system is slow" into "this downstream call is slow."az X-Ray (vagy OpenTelemetry) egy kérést követ szolgáltatásokon át, a „a rendszer lassú"-t „ez a lejjebbi hívás lassú"-vá alakítva.
  • logsCloudWatch Logs / OpenSearch for querying, with older logs archived to S3 cheaply. Logs explain why once a metric or trace tells you where to look.CloudWatch Logs / OpenSearch a lekérdezéshez, a régebbi logok olcsón S3-ba archiválva. A logok megmagyarázzák, miért, ha egy metrika vagy trace megmondta, hol nézz.
  • audit + threatsCloudTrail records API activity (the audit trail); GuardDuty watches for anomalous behaviour. Separate from app observability but fed by the same discipline.a CloudTrail API-aktivitást rögzít (az audit-nyom); a GuardDuty anomális viselkedést figyel. Elkülönül az app-observability-től, de ugyanaz a fegyelem táplálja.

Why this shapeMiért ez a formaYou need all three pillars: a metric flags that latency spiked, a trace localises which service, the logs explain the cause. The alerting discipline is what keeps it useful — alarm on user-facing symptoms, not on everything, or on-call fatigue sets in and real alerts get ignored. Archiving logs to S3 keeps retention affordable while staying queryable via Athena.Mindhárom pillér kell: egy metrika jelzi, hogy a késleltetés megugrott, egy trace lokalizálja, melyik szolgáltatás, a logok megmagyarázzák az okot. A riasztási fegyelem tartja hasznosnak — a felhasználó-felé néző tünetekre riassz, ne mindenre, különben beáll az on-call fáradtság, és a valódi riasztásokat figyelmen kívül hagyják. A logok S3-ba archiválása megfizethetően tartja a megőrzést, míg Athenán át lekérdezhető marad.

Security-Focused Design (Defence in Depth)Biztonság-fókuszú terv (mélységi védelem)

SolvesMit old megprotecting the same web app in layers, so that a single misconfiguration or leak isn't enough for an attacker to get in.ugyanazon webapp védelme rétegekben, hogy egyetlen hibás konfiguráció vagy szivárgás ne legyen elég egy támadónak a bejutáshoz.
Made ofMiből állthe 3-tier app, with each defence layer marked: WAF at the edge → NACL at the subnet edge → the security-group chain → encryption + secrets management at the data layer.a 3-rétegű app, minden védelmi réteg megjelölve: WAF az élen → NACL a subnet-élen → a security-group lánc → titkosítás + titok-kezelés az adatrétegben.

The same 3-tier app, drawn to show every security layer a request must pass. Nothing here is a single line of defence — an attacker has to get through the edge, then the subnet boundary, then each security group, then encryption, at every step. This is defence in depth: layered controls so no single failure is a breach.Ugyanaz a 3-rétegű app, úgy rajzolva, hogy minden biztonsági réteget mutasson, amin egy kérésnek át kell jutnia. Semmi itt nem egyetlen védelmi vonal — egy támadónak át kell jutnia az élen, majd a subnet-határon, majd minden security groupon, majd a titkosításon, minden lépésnél. Ez a mélységi védelem: rétegzett kontrollok, hogy egyetlen hiba se legyen betörés.

Key settings — the layers, outside inKulcs-beállítások — a rétegek, kívülről befelé

  • edgeCloudFront + WAF filters malicious requests (SQL injection, bad bots) and absorbs DDoS before traffic reaches the VPC.a CloudFront + WAF kiszűri a rosszindulatú kéréseket (SQL injection, rossz botok) és elnyeli a DDoS-t, mielőtt a forgalom elérné a VPC-t.
  • NACLstateless subnet-edge rules — a coarse allow/deny layer beneath the security groups, useful to block a known-bad IP range subnet-wide.állapotmentes subnet-él szabályok — egy durva allow/deny réteg a security groupok alatt, hasznos egy ismert-rossz IP-tartomány subnet-szintű blokkolására.
  • SG chainthe stateful core: sg-alb (443 from internet) → sg-app (from sg-alb only) → sg-db (from sg-app only). Each tier trusts only the one above it, by SG reference not IP.az állapottartó mag: sg-alb (443 az internetről) → sg-app (csak sg-alb-ből) → sg-db (csak sg-app-ből). Minden réteg csak a fölötte lévőben bízik, SG-hivatkozással, nem IP-vel.
  • data layerRDS encrypted at rest with KMS; the app pulls credentials from Secrets Manager at runtime (never hardcoded). IAM roles govern who/what can reach each service.az RDS nyugalmi állapotban KMS-sel titkosítva; az app futásidőben húzza a hitelesítő adatokat a Secrets Managerből (sosem beégetve). Az IAM role-ok szabályozzák, ki/mi érhet el minden szolgáltatást.

Why this shapeMiért ez a formaNo single control is a strategy — the point is that a gap in one layer is caught by the next. A misconfigured security group is still backstopped by the NACL and the fact that the subnet is private; a leaked endpoint is still behind WAF and IAM. For compliance (GDPR/HIPAA), add region pinning via SCPs, encryption everywhere, and CloudTrail + Config as the provable audit trail. Least privilege on every IAM role is the thread running through all of it.Egyetlen kontroll sem stratégia — a lényeg, hogy egy réteg rés/hézagát a következő elkapja. Egy rosszul konfigurált security groupot még mindig tartalékol a NACL és az, hogy a subnet privát; egy kiszivárgott endpoint még mindig a WAF és IAM mögött van. Compliance-hez (GDPR/HIPAA) adj hozzá régió-rögzítést SCP-kkel, titkosítást mindenhol, és CloudTrail + Config-ot mint bizonyítható audit-nyomot. A legkisebb jogosultság minden IAM role-on a szál, ami végigfut az egészen.

Multi-Account Governance (Landing Zone)Multi-account governance (landing zone)

SolvesMit old megmanaging many projects or clients cleanly at scale — keeping each walled off, billing separate, and one set of rules enforced everywhere.sok projekt vagy ügyfél tiszta kezelése nagy léptékben — mindegyik elfalazva, számlázás elkülönítve, és egy szabálykészlet mindenhol kikényszerítve.
Made ofMiből állmany AWS accounts under one Organization: shared core accounts (logging, security, identity) + one account per team/environment, with org-wide guardrails (SCPs) nobody can override.sok AWS-account egy Organization alatt: megosztott központi accountok (logolás, biztonság, identitás) + egy account csapatonként/környezetenként, org-szintű védőkorlátokkal (SCP-k), amiket senki nem írhat felül.

How an organisation — especially a consultancy managing many clients — structures AWS at scale. Instead of one big account, you split into many, grouped under an Organization with guardrails that no member account can override. Core shared accounts handle logging, security, and identity centrally; each team-and-environment gets its own isolated account.Ahogy egy szervezet — különösen egy sok ügyfelet kezelő tanácsadó — nagy léptékben strukturálja az AWS-t. Egy nagy account helyett sokra osztod, egy Organization alá csoportosítva védőkorlátokkal, amiket egyetlen tag-account sem írhat felül. A központi megosztott accountok a logolást, biztonságot, és identitást központilag kezelik; minden csapat-és-környezet saját izolált accountot kap.

Key settings — accounts as the isolation boundaryKulcs-beállítások — accountok mint izolációs határ

  • SCPsorg-wide guardrails: "only eu-* regions," "CloudTrail can't be disabled," "no root access keys." These cap what any account can do — they restrict, never grant.org-szintű védőkorlátok: „csak eu-* régiók", „a CloudTrail nem tiltható le", „nincs root access key". Ezek korlátozzák, mit tehet egy account — korlátoznak, sosem adnak.
  • core accountsa Log Archive account aggregates all CloudTrail; a Security account runs GuardDuty; Shared Services holds networking and CI; Identity (IAM Identity Center / SSO) is the single sign-on point.egy Log Archive account aggregálja az összes CloudTrailt; egy Security account futtatja a GuardDutyt; a Shared Services tartja a hálózatot és CI-t; az Identity (IAM Identity Center / SSO) az egyetlen bejelentkezési pont.
  • workload accountsone per team × environment (Team A prod, Team A dev, …). An account is the hardest blast-radius boundary AWS offers — a mistake in dev can't touch prod.egy csapatonként × környezetenként (Team A prod, Team A dev, …). Egy account a legkeményebb blast-radius határ, amit az AWS kínál — egy hiba a devben nem érhet a prodhoz.
  • accessnobody has standing access — people authenticate once at SSO, then assume a scoped, temporary role in the target account, with an audit trail of who assumed what.senkinek nincs állandó hozzáférése — az emberek egyszer autentikálnak az SSO-nál, majd felvesznek egy szűkített, ideiglenes role-t a cél-accountban, audit-nyommal arról, ki mit vett fel.

Why this shapeMiért ez a formaSeparate accounts give the strongest isolation AWS has — far stronger than IAM boundaries within one account. For a consultancy this is the foundation: each client (and each environment) is walled off, billing is cleanly separated, and org-wide SCPs enforce baseline policy everywhere at once. Control Tower sets this whole landing zone up with best practices baked in, rather than assembling it by hand.A külön accountok adják a legerősebb izolációt, amit az AWS-nek van — messze erősebb, mint az IAM-határok egy accounton belül. Egy tanácsadónak ez az alap: minden ügyfél (és minden környezet) el van falazva, a számlázás tisztán elkülönül, és az org-szintű SCP-k egyszerre kényszerítik ki mindenhol az alap-policy-t. A Control Tower ezt az egész landing zone-t beépített best practice-ekkel állítja fel, ahelyett hogy kézzel raknád össze.

OIDC Pipeline AuthenticationOIDC pipeline-autentikáció

SolvesMit old megletting your CI/CD pipeline deploy to AWS without storing a permanent password/key anywhere — which is exactly what usually leaks.a CI/CD pipeline AWS-re telepítése anélkül, hogy bárhol állandó jelszót/kulcsot tárolnál — ami pont ami általában kiszivárog.
Made ofMiből álla 4-step token exchange: the pipeline proves its identity with a short-lived token → AWS verifies it → grants a temporary role → issues credentials that expire in ~1 hour.egy 4-lépéses token-csere: a pipeline egy rövid életű tokennel bizonyítja identitását → az AWS ellenőrzi → ideiglenes role-t ad → ~1 óra alatt lejáró hitelesítő adatokat bocsát ki.

How a CI/CD pipeline authenticates to AWS without storing long-lived access keys — the modern best practice, and the one that's hard to picture from text alone. Instead of a secret sitting in the CI system, the pipeline proves its identity with a short-lived token that AWS exchanges for temporary credentials, minted fresh for each run.Ahogy egy CI/CD pipeline autentikál az AWS felé anélkül, hogy hosszú életű access key-eket tárolna — a modern best practice, és az, amit nehéz elképzelni pusztán szövegből. Ahelyett hogy egy titok ülne a CI-rendszerben, a pipeline egy rövid életű tokennel bizonyítja identitását, amit az AWS ideiglenes hitelesítő adatokra vált, minden futáshoz frissen készítve.

Key settings — the exchange, step by stepKulcs-beállítások — a csere, lépésről lépésre

  • 1 · tokenthe pipeline job requests a signed OIDC token from its CI provider — this token encodes the job's identity (which repo, which branch, which workflow).a pipeline job egy aláírt OIDC tokent kér a CI-szolgáltatójától — ez a token kódolja a job identitását (melyik repo, melyik branch, melyik workflow).
  • 2 · verifyAWS's IAM OIDC provider verifies the token's signature against the trusted issuer, and checks it against the role's trust policy — which is scoped to this repo, this branch only.az AWS IAM OIDC providere ellenőrzi a token aláírását a megbízható kibocsátóval szemben, és összeveti a role trust policy-jával — ami erre a repóra, csak erre a branchre van szűkítve.
  • 3 · assumeif it matches, STS lets the job assume the IAM role — granting exactly the permissions that role holds, nothing more.ha egyezik, az STS engedi a jobnak felvenni az IAM role-t — pontosan a role jogosultságait adva, semmivel sem többet.
  • 4 · credentialsSTS returns short-lived credentials (typically ~1 hour) that the deploy step uses. They expire on their own — nothing to rotate, nothing to leak.az STS rövid életű hitelesítő adatokat ad vissza (jellemzően ~1 óra), amit a deploy-lépés használ. Maguktól lejárnak — nincs mit rotálni, nincs mi kiszivárogjon.

Why this shapeMiért ez a formaThe whole win is that no long-lived AWS secret ever exists in the CI system — which is exactly where credential leaks come from. The trust policy scoped to a specific repo and branch means even if someone forks or opens a rogue branch, they can't assume the role. If your interview answer for pipeline auth is "store an access key as a CI secret," this is the follow-up they're waiting for: "why not OIDC?" Being able to walk these four steps is the strong answer.Az egész nyereség, hogy soha nem létezik hosszú életű AWS-titok a CI-rendszerben — ami pontosan az, ahonnan a credential-szivárgások jönnek. A konkrét repóra és branchre szűkített trust policy azt jelenti, hogy még ha valaki forkol vagy nyit egy szélhámos branchet, nem tudja felvenni a role-t. Ha az interjú-válaszod a pipeline-authra „tárolj egy access key-t CI-titokként", ez a folytatás, amire várnak: „miért nem OIDC?" E négy lépés végigvezetése az erős válasz.
