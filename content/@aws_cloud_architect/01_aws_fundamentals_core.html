Region & Availability ZoneRégió & Availability Zone

A Region is a geographic location (eu-central-1 = Frankfurt); an Availability Zone (AZ) is one of several isolated fault domains inside it.A régió egy földrajzi hely (eu-central-1 = Frankfurt); egy Availability Zone (AZ) az azon belüli több izolált fault domain egyike.

  • What it isMi ezAn AZ is one or more discrete data centres with independent power and networking. A region has several (usually 3+). Your resources live in a specific region and AZ.Egy AZ egy vagy több különálló adatközpont független áramellátással és hálózattal. Egy régióban több van (általában 3+). Az erőforrásaid egy konkrét régióban és AZ-ban élnek.
  • What it's forMire valóSpreading across AZs is how you survive a data-centre failure. This is the foundation of all high availability on AWS.Az AZ-k közti szétosztás az, ahogy túléled egy adatközpont hibáját. Ez minden AWS magas rendelkezésre állás alapja.
  • Interview pointInterjú-lényegMulti-AZ = surviving an AZ outage within one region (the default for production). Multi-region = surviving a whole-region outage (rare, expensive). Don't confuse them.Multi-AZ = egy AZ-kiesés túlélése egy régión belül (a produkciós alapértelmezés). Multi-region = egy teljes régió-kiesés túlélése (ritka, drága). Ne keverd őket.

VPC (Virtual Private Cloud)VPC (Virtual Private Cloud)

Your own private, isolated network inside AWS — you define its IP address range and carve it into subnets.A saját privát, izolált hálózatod az AWS-en belül — te definiálod az IP-tartományát, és subnetekre osztod.

  • What it isMi ezA logically isolated section of AWS where you launch resources. You give it a CIDR block (e.g. 10.0.0.0/16) that defines its private IP range.Az AWS logikailag izolált szelete, ahol erőforrásokat indítasz. Adsz neki egy CIDR blokkot (pl. 10.0.0.0/16), ami a privát IP-tartományát definiálja.
  • What it's forMire valóIt's the network boundary around everything: which resources can talk to each other, what's reachable from the internet, and what stays private is all decided here.Ez a hálózati határ minden körül: mely erőforrások beszélhetnek egymással, mi érhető el az internetről, és mi marad privát — mind itt dől el.
  • Interview pointInterjú-lényegA VPC spans a region and contains subnets, each of which lives in one AZ. The standard design: public subnets for internet-facing bits, private subnets for everything else, spread across AZs.Egy VPC egy régiót fed le, és subneteket tartalmaz, amelyek mindegyike egy AZ-ban él. A standard terv: publikus subnetek az internet felé néző részeknek, privát subnetek minden másnak, AZ-k között szétosztva.
03

SubnetSubnet

A slice of a VPC's IP range that lives in one AZ. "Public" or "private" depending on whether it can route to the internet.Egy VPC IP-tartományának egy szelete, ami egy AZ-ban él. „Publikus" vagy „privát" attól függően, tud-e az internetre útvonalazni.

  • What it isMi ezA sub-range of the VPC CIDR (e.g. 10.0.1.0/24) tied to a single AZ. Every resource with a network interface sits in a subnet.A VPC CIDR egy al-tartománya (pl. 10.0.1.0/24) egyetlen AZ-hoz kötve. Minden hálózati interfésszel rendelkező erőforrás egy subnetben ül.
  • Public vs privatePublikus vs privátThe difference is the route table: a public subnet has a route to an Internet Gateway; a private one doesn't (it reaches out via NAT instead). Nothing else distinguishes them.A különbség a route table: egy publikus subnetnek van útvonala egy Internet Gateway-hez; egy privátnak nincs (helyette NAT-on át nyúl ki). Semmi más nem különbözteti meg őket.
  • Interview pointInterjú-lényegPut only internet-facing resources (load balancer, NAT) in public subnets; put app servers and databases in private ones. And spread each tier across at least two AZs.Csak internet felé néző erőforrásokat (load balancer, NAT) tegyél publikus subnetbe; az app-szervereket és adatbázisokat privátba. És minden réteget osszp szét legalább két AZ között.
04

Route TableRoute table

The rules that decide where network traffic goes — attached to subnets, it maps destination IP ranges to targets (a gateway, an endpoint, etc.).A szabályok, amelyek eldöntik, hova megy a hálózati forgalom — subnetekhez kapcsolva, cél-IP-tartományokat célokhoz (gateway, endpoint, stb.) rendel.

  • What it isMi ezA set of routes: "traffic for this IP range goes to that target." Each subnet is associated with one route table. A local route for the VPC's own range always exists.Útvonalak halmaza: „az erre az IP-tartományra menő forgalom arra a célra megy." Minden subnet egy route table-höz van társítva. A VPC saját tartományához mindig van egy local útvonal.
  • What it's forMire valóThis is literally what makes a subnet public or private — a route 0.0.0.0/0 → Internet Gateway makes it public. A route to a NAT gateway gives private subnets outbound-only internet.Ez szó szerint az, ami egy subnetet publikussá vagy priváttá tesz — egy 0.0.0.0/0 → Internet Gateway útvonal publikussá teszi. Egy NAT gateway-hez menő útvonal csak-kimenő internetet ad a privát subneteknek.
  • Interview pointInterjú-lényeg"Why can't my private instance reach the internet?" is very often a missing or wrong route table entry. It's the first thing to check on a connectivity problem, right after security groups.A „miért nem éri el a privát instance-om az internetet?" nagyon gyakran egy hiányzó vagy rossz route table bejegyzés. Ez az első, amit ellenőrzöl egy kapcsolat-problémánál, rögtön a security groupok után.
05

Internet Gateway & NAT GatewayInternet Gateway & NAT Gateway

The Internet Gateway (IGW) connects a VPC to the internet; a NAT Gateway lets private subnets reach out without being reachable.Az Internet Gateway (IGW) összeköti a VPC-t az internettel; egy NAT Gateway lehetővé teszi, hogy a privát subnetek kinyúljanak anélkül, hogy elérhetők lennének.

  • Internet GatewayInternet GatewayOne per VPC, it's the door to the internet. A resource is internet-reachable only if it's in a subnet whose route table points to the IGW and it has a public IP.Egy VPC-nként, ez az ajtó az internetre. Egy erőforrás csak akkor érhető el az internetről, ha olyan subnetben van, aminek a route table-je az IGW-re mutat, és van publikus IP-je.
  • NAT GatewayNAT GatewaySits in a public subnet; lets private-subnet resources make outbound connections (download updates, call APIs) while staying unreachable from the internet. Outbound only.Egy publikus subnetben ül; lehetővé teszi a privát-subnet erőforrásoknak a kimenő kapcsolatokat (frissítések letöltése, API-hívás), miközben elérhetetlenek maradnak az internetről. Csak kimenő.
  • Interview pointInterjú-lényegNAT gateways cost money (per hour + per GB), so in production you run one per AZ (to avoid cross-AZ cost and an AZ dependency), and use VPC endpoints for AWS-bound traffic to skip NAT entirely.A NAT gateway-ek pénzbe kerülnek (óránként + GB-onként), tehát produkcióban AZ-nként egyet futtatsz (a cross-AZ költség és az AZ-függőség elkerülésére), és VPC endpointot használsz az AWS felé menő forgalomhoz, hogy teljesen kihagyd a NAT-ot.
06

Security GroupSecurity Group

A stateful virtual firewall attached to a resource (like an EC2 instance) — allow rules only, and return traffic is automatic.Egy állapottartó virtuális tűzfal egy erőforráshoz (pl. egy EC2 instance-hoz) kapcsolva — csak allow szabályok, és a visszatérő forgalom automatikus.

  • What it isMi ezA set of rules controlling inbound and outbound traffic for the resources it's attached to. You only write allow rules — anything not allowed is denied.Szabályok halmaza, amely a hozzá kapcsolt erőforrások bejövő és kimenő forgalmát vezérli. Csak allow szabályokat írsz — ami nincs engedélyezve, az tiltott.
  • StatefulÁllapottartó"Stateful" means if you allow an inbound request, the response is allowed back automatically — you don't write a return rule. This is the key difference from a NACL.Az „állapottartó" azt jelenti, hogy ha engedélyezel egy bejövő kérést, a válasz automatikusan visszaengedett — nem írsz visszatérési szabályt. Ez a kulcskülönbség egy NACL-lel szemben.
  • Interview pointInterjú-lényegSecurity groups do ~all the real access control. A clean pattern: the app's SG allows inbound only from the load balancer's SG, and the database's SG allows inbound only from the app's SG — referencing SGs, not IP ranges.A security groupok végzik ~az összes valódi hozzáférés-vezérlést. Tiszta minta: az app SG-je csak a load balancer SG-jéből enged bejövőt, és az adatbázis SG-je csak az app SG-jéből — SG-kre hivatkozva, nem IP-tartományokra.
07

NACL (Network ACL)NACL (Network ACL)

A stateless firewall at the subnet level — has both allow and deny rules, and evaluates each direction independently.Egy állapotmentes tűzfal a subnet szintjén — allow és deny szabálya is van, és mindkét irányt függetlenül értékeli.

  • What it isMi ezA numbered list of allow/deny rules attached to a subnet, filtering all traffic in and out of it. Rules are evaluated in order until one matches.Számozott allow/deny szabályok listája egy subnethez kapcsolva, amely szűri a be- és kimenő forgalmat. A szabályok sorrendben értékelődnek, míg egy nem illik.
  • StatelessÁllapotmentesUnlike a security group, return traffic is not automatic — if you allow an inbound request, you must also explicitly allow the outbound response (on the ephemeral port range). Forgetting this is a classic bug.Egy security grouppal ellentétben a visszatérő forgalom nem automatikus — ha engedélyezel egy bejövő kérést, explicit engedélyezned kell a kimenő választ is (az ephemeral port-tartományon). Ennek elfelejtése klasszikus hiba.
  • Interview pointInterjú-lényegSG vs NACL is a favourite question: security group = stateful, instance-level, allow-only; NACL = stateless, subnet-level, allow + deny. In practice SGs do the work; NACLs are a coarse backstop, often to block a specific bad IP.Az SG vs NACL kedvenc kérdés: security group = állapottartó, instance-szintű, csak-allow; NACL = állapotmentes, subnet-szintű, allow + deny. A gyakorlatban az SG-k végzik a munkát; a NACL-ök durva tartalék, gyakran egy konkrét rossz IP blokkolására.

VPC Endpoint & PrivateLinkVPC Endpoint & PrivateLink

A private door from your VPC to an AWS service, so the traffic never touches the public internet.Egy privát ajtó a VPC-dből egy AWS szolgáltatáshoz, hogy a forgalom sose érintse a nyilvános internetet.

  • Two typesKét típusA gateway endpoint (for S3 and DynamoDB) adds a route so traffic to them stays internal — free. An interface endpoint (for most other services, powered by PrivateLink) puts a private IP in your subnet for the service.Egy gateway endpoint (S3-hoz és DynamoDB-hez) hozzáad egy útvonalat, hogy a hozzájuk menő forgalom belül maradjon — ingyenes. Egy interface endpoint (a legtöbb más szolgáltatáshoz, PrivateLinkkel hajtva) egy privát IP-t tesz a subnetedbe a szolgáltatásnak.
  • What it's forMire valóTwo wins: it keeps data off the public internet (a compliance requirement), and it removes NAT gateway cost for that traffic — reaching S3 without a NAT is the canonical example.Két nyereség: távol tartja az adatot a nyilvános internettől (compliance-követelmény), és megszünteti a NAT gateway költséget arra a forgalomra — az S3 elérése NAT nélkül a kanonikus példa.
  • Interview pointInterjú-lényegIf someone mentions high NAT cost from private instances pulling from S3, the answer is a gateway endpoint. PrivateLink is also how you reach Bedrock and other services privately.Ha valaki magas NAT-költséget említ privát instance-okból, amelyek S3-ból húznak, a válasz egy gateway endpoint. A PrivateLink az is, ahogy a Bedrockot és más szolgáltatásokat privátan elérsz.

Route 53 (DNS)Route 53 (DNS)

AWS's DNS service — turns names (yoursite.com) into addresses, and can route traffic intelligently.Az AWS DNS-szolgáltatása — neveket (yoursite.com) címekké alakít, és intelligensen tud forgalmat irányítani.

  • What it isMi ezA managed, highly available DNS. You host a domain's records here; it answers DNS queries and can do health checks and failover.Egy menedzselt, magasan rendelkezésre álló DNS. Egy domain rekordjait itt tárolod; megválaszolja a DNS-lekérdezéseket, és tud health checket és failovert.
  • Routing policiesÚtválasztási policy-kBeyond simple lookups: weighted (send X% of traffic to one target — used for gradual rollouts), latency-based, failover (switch to a backup if the primary is unhealthy), and geolocation.Az egyszerű kereséseken túl: weighted (a forgalom X%-át egy célra küldi — fokozatos kiadáshoz), latency-alapú, failover (átvált egy tartalékra, ha a primary beteg), és geolokáció.
  • Interview pointInterjú-lényegIn a migration, a low DNS TTL makes cutover and rollback fast (records propagate quickly). But a low TTL alone doesn't shift traffic gradually — that needs weighted records.Egy migrációban egy alacsony DNS TTL gyorssá teszi az átállást és a visszagörgetést (a rekordok gyorsan propagálódnak). De egy alacsony TTL önmagában nem tolja a forgalmat fokozatosan — ahhoz weighted rekordok kellenek.

CloudFront (CDN)CloudFront (CDN)

AWS's content delivery network — caches content at edge locations worldwide so users get it from somewhere near them.Az AWS tartalomkézbesítő hálózata — edge helyeken cache-eli a tartalmat világszerte, hogy a felhasználók egy közeli helyről kapják.

  • What it isMi ezA CDN with a global network of edge caches. It sits in front of an origin (S3, a load balancer) and serves cached copies from the edge closest to each user.Egy CDN globális edge-cache hálózattal. Egy origin (S3, egy load balancer) elé ül, és a gyorsítótárazott másolatokat a minden felhasználóhoz legközelebbi edge-ről szolgálja.
  • What it's forMire valóLower latency (content is physically closer), less load on your origin, and lower cost (edge cache hits are cheaper than origin fetches). Also a security layer (it can sit in front with WAF).Alacsonyabb késleltetés (a tartalom fizikailag közelebb), kevesebb terhelés az originen, és alacsonyabb költség (az edge-cache találatok olcsóbbak, mint az origin-lekérések). Egyben biztonsági réteg is (WAF-fal elé ülhet).
  • Interview pointInterjú-lényegThe right way to serve public content from S3: don't make the bucket public — put CloudFront in front with Origin Access Control so the bucket only trusts CloudFront.A helyes mód publikus tartalmat S3-ból kiszolgálni: ne tedd publikussá a bucketet — tegyél elé CloudFrontot Origin Access Controllal, hogy a bucket csak a CloudFrontban bízzon.

IAM & the Shared Responsibility ModelIAM & a megosztott felelősség modell

IAM controls who can do what in your account. The shared responsibility model splits security: AWS secures the cloud, you secure what's in it.Az IAM vezérli, ki mit tehet az accountodban. A megosztott felelősség modell felosztja a biztonságot: az AWS a felhőt biztosítja, te azt, ami benne van.

  • IAMIAMIdentity and Access Management: the system of users, roles, and policies that grant or deny permissions to every action and resource in AWS.Identity and Access Management: a userek, role-ok és policy-k rendszere, amely minden AWS-műveletre és -erőforrásra megad vagy megtagad jogosultságot.
  • Shared responsibilityMegosztott felelősségAWS handles the hardware, data centres, and managed-service internals. You handle IAM, data encryption, network config, and (on EC2) OS patching. Most breaches are on the customer's side of this line.Az AWS kezeli a hardvert, adatközpontokat, és a menedzselt-szolgáltatás belsőket. Te kezeled az IAM-et, adattitkosítást, hálózati konfigot, és (EC2-n) az OS-patchelést. A legtöbb betörés a vonal ügyfél-oldalán van.
  • Interview pointInterjú-lényegThe line moves with the service: on EC2 you patch the OS; on Fargate or Lambda, AWS does. Knowing where the responsibility sits per service is the point.A vonal a szolgáltatással mozog: EC2-n te patcheled az OS-t; Fargate-en vagy Lambdán az AWS. A lényeg tudni, hol a felelősség szolgáltatásonként.

IAM Roles vs Users vs PoliciesIAM role-ok vs userek vs policy-k

A policy is a document granting permissions; a user is a person with long-lived credentials; a role is an identity assumed temporarily (no stored keys).Egy policy egy jogosultságot adó dokumentum; egy user egy személy hosszú életű hitelesítő adatokkal; egy role egy ideiglenesen felvett identitás (nincs tárolt kulcs).

  • PolicyPolicyA JSON document listing allowed/denied actions on resources. Attached to a user, role, or resource. This is where permissions actually live.Egy JSON dokumentum, amely engedélyezett/tiltott műveleteket sorol fel erőforrásokon. Userhez, role-hoz vagy erőforráshoz kapcsolva. Itt laknak valójában a jogosultságok.
  • Role vs userRole vs userA role grants temporary credentials — assumed by a service, an EC2 instance, or a pipeline, with no long-lived keys to leak. A user has permanent access keys. Prefer roles for workloads, and federation (SSO) for humans.Egy role ideiglenes hitelesítő adatokat ad — egy szolgáltatás, EC2 instance vagy pipeline veszi fel, hosszú életű kulcs nélkül, ami kiszivároghatna. Egy usernek állandó access key-e van. Preferáld a role-okat workloadokhoz, és a föderációt (SSO) embereknek.
  • Interview pointInterjú-lényeg"Roles over users" is the standard modern answer. Access keys stored somewhere are the source of most credential leaks — a role hands out short-lived credentials instead.A „role-ok user helyett" a standard modern válasz. A valahol tárolt access key-ek a legtöbb credential-szivárgás forrása — egy role helyette rövid életű hitelesítő adatokat oszt.

How IAM Policies ResolveHogyan dőlnek el az IAM policy-k

Default deny. An explicit allow grants; an explicit deny overrides everything. Within an account, identity and resource policies combine; boundaries and SCPs only restrict.Alapból deny. Egy explicit allow ad; egy explicit deny mindent felülír. Egy accounton belül az identity- és resource-policy-k kombinálódnak; a boundary-k és SCP-k csak korlátoznak.

  • The orderA sorrendEverything is denied unless allowed. An explicit Allow grants access. An explicit Deny anywhere always wins. So: granted by identity or resource policy, capped by boundaries/SCPs, killed by any deny.Minden tiltott, hacsak nem engedélyezett. Egy explicit Allow ad hozzáférést. Egy explicit Deny bárhol mindig nyer. Tehát: identity- vagy resource-policy ad, boundary-k/SCP-k korlátoznak, bármely deny megöl.
  • The layersA rétegekIdentity policies (on the user/role), resource policies (on the S3 bucket, etc.), permission boundaries, and SCPs (org-wide guardrails). Within one account, identity + resource combine (union), the others only restrict.Identity policy-k (a useren/role-on), resource policy-k (az S3 bucketen, stb.), permission boundary-k, és SCP-k (org-szintű védőkorlátok). Egy accounton belül az identity + resource kombinálódik (unió), a többi csak korlátoz.
  • Interview pointInterjú-lényegThe common mistake in the wild is over-broad policies: "s3:*" on "*". Least privilege — scope to the specific actions and resources needed — is what a security review looks for.A gyakori hiba a vadonban a túl tág policy: "s3:*" a "*"-on. A legkisebb jogosultság — a konkrét szükséges műveletekre és erőforrásokra szűkítés — az, amit egy biztonsági review keres.

EC2 (Elastic Compute Cloud)EC2 (Elastic Compute Cloud)

Virtual servers in the cloud — you pick the size, OS, and count, and you manage everything on them.Virtuális szerverek a felhőben — kiválasztod a méretet, OS-t és darabszámot, és mindent te kezelsz rajtuk.

  • What it isMi ezResizable virtual machines. You choose an instance type (CPU/memory), an OS image, and networking; you're responsible for the OS, patching, scaling, and what runs on it.Átméretezhető virtuális gépek. Kiválasztasz egy instance-típust (CPU/memória), egy OS-image-et, és hálózatot; te felelsz az OS-ért, patchelésért, skálázásért, és azért, ami rajta fut.
  • What it's forMire valóMaximum control and flexibility — legacy apps, special hardware needs, or anything that doesn't fit a managed service. The most "hands-on" compute option.Maximális kontroll és rugalmasság — legacy appok, speciális hardver-igények, vagy bármi, ami nem illik egy menedzselt szolgáltatásba. A leginkább „hands-on" számítási opció.
  • Interview pointInterjú-lényegEC2 is one end of a spectrum from "you manage everything" (EC2) to "you manage nothing but the function" (Lambda). Reach for it when you genuinely need the control; otherwise a managed option is usually better.Az EC2 egy vége egy spektrumnak a „mindent te kezelsz" (EC2) és a „semmit nem kezelsz a függvényen kívül" (Lambda) között. Akkor nyúlj hozzá, ha tényleg kell a kontroll; egyébként egy menedzselt opció általában jobb.

Containers: ECS, EKS & FargateKonténerek: ECS, EKS & Fargate

Ways to run containers on AWS. ECS is the simple AWS-native orchestrator; EKS is managed Kubernetes; Fargate is the "serverless" mode that removes server management.Módok konténerek futtatására AWS-en. Disaster Recovery: RTO & RPOKatasztrófa-helyreállítás: RTO & RPO

  • RTO vs RPORTO vs RPORTO (Recovery Time Objective) = the downtime window, how long until you're running again. A daily backup = up to 24h RPO.RTO (Recovery Time Objective) = a leállási ablak, meddig tart, míg újra futsz. RPO (Recovery Point Objective) = az adatvesztési ablak, meddig nyúlik vissza az utolsó helyreállítható állapotod. Egy napi mentés = akár 24h RPO.
  • The four strategiesA négy stratégiaBy cost and speed: Backup & Restore (cheapest, hours) → Pilot Light (core running, scale up) → Warm Standby (scaled-down live copy) → Active-Active (multi-region, near-zero RTO, priciest).Költség és sebesség szerint: Backup & Restore (legolcsóbb, órák) → Pilot Light (mag fut, felskálázás) → Warm Standby (kicsinyített élő másolat) → Active-Active (multi-region, közel nulla RTO, legdrágább).
  • Interview pointInterjú-lényegLet the requirement pick the strategy: "how long can this be down, how much data can we lose?" then match the cheapest option that meets it. And a DR plan that's never been tested is a hypothesis, not a plan.Hagyd, hogy a követelmény válassza a stratégiát: „meddig lehet ez leállva, mennyi adatot veszíthetünk?" majd illeszd a legolcsóbb megfelelő opciót.
