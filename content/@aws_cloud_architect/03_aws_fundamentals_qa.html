What's the difference between a security group and a NACL?What is the difference between a security group and a NACL?Mi a különbség egy security group és egy NACL között?

  • Security group: stateful, attached to a resource (instance-level), allow rules only, return traffic automatic. NACL: stateless, attached to a subnet, allow and deny rules, each direction evaluated independently (so you must allow the return ephemeral ports). In practice SGs do the real work; NACLs are a coarse subnet backstop.A security group is stateful. It is attached to a resource (one instance). It has allow rules only, and reply traffic is let back in automatically. A NACL is stateless. It is attached to a subnet, has both allow and deny rules, and each direction is checked on its own — so you must also allow the reply ports. In real use, security groups do the main work; a NACL is just a rough extra layer on the subnet.A security group stateful (állapottartó): egy erőforráshoz (egy instance-hoz) van kötve, csak allow szabályai vannak, és a válaszforgalmat automatikusan visszaengedi. A NACL stateless (állapotmentes): egy subnethez van kötve, allow és deny szabálya is van, és mindkét irányt külön értékeli — tehát a válasz ephemeral portjait is engedélyezned kell. A gyakorlatban a security group végzi az érdemi munkát; a NACL csak egy durva, subnet-szintű extra réteg.

What makes a subnet "public"?What makes a subnet "public"?Mitől lesz egy subnet „public"?

  • A route in its route table pointing 0.0.0.0/0 to an Internet Gateway. That's the only thing — a "private" subnet simply lacks that route and reaches the internet (if at all) via a NAT gateway instead.One thing only: a route in its route table that sends 0.0.0.0/0 to an Internet Gateway. A "private" subnet just does not have that route. It reaches the internet (if it needs to) through a NAT gateway instead.Egyetlen dolog: a route table-jében van egy route, ami a 0.0.0.0/0-t egy Internet Gateway felé küldi. Egy „private" subnetnek egyszerűen nincs ilyen route-ja — ha kell neki internet, azt egy NAT gateway-en át éri el.

How does a private instance download OS updates?How does a private instance download OS updates?Hogyan tölt le egy private instance OS-frissítéseket?

  • Through a NAT gateway in a public subnet — it lets private resources make outbound connections while staying unreachable from the internet. For AWS services specifically (like S3), a VPC endpoint is better: it avoids NAT cost and keeps traffic off the public internet.Through a NAT gateway that sits in a public subnet. It lets private resources start outbound connections, but nothing on the internet can reach them. For AWS services like S3, a VPC endpoint is better: it costs less than NAT and keeps the traffic off the public internet.Egy public subnetben lévő NAT gateway-en át — ez engedi, hogy a private erőforrások kifelé kapcsolatot indítsanak, miközben az internet felől nem elérhetők. Kifejezetten AWS-szolgáltatásokhoz (pl. S3) jobb egy VPC endpoint: olcsóbb, mint a NAT, és a forgalom nem megy ki a publikus internetre.

When would you use a VPC endpoint?When would you use a VPC endpoint?Mikor használnál VPC endpointot?

  • To reach an AWS service privately without traffic leaving the AWS network. A gateway endpoint (S3, DynamoDB) is free and removes NAT cost for that traffic; an interface endpoint (PrivateLink) covers other services. Canonical use: reaching S3 from a private subnet without a NAT gateway.To reach an AWS service privately, without the traffic leaving the AWS network. A gateway endpoint (for S3 and DynamoDB) is free and removes the NAT cost for that traffic. An interface endpoint (PrivateLink) covers the other services. The classic use: reach S3 from a private subnet without a NAT gateway.Hogy egy AWS-szolgáltatást privátban érj el úgy, hogy a forgalom nem hagyja el az AWS-hálózatot. Egy gateway endpoint (S3, DynamoDB) ingyenes, és megspórolja a NAT-költséget arra a forgalomra; egy interface endpoint (PrivateLink) a többi szolgáltatást fedi le. Tipikus eset: S3 elérése egy private subnetből NAT gateway nélkül.

What's the difference between an IAM role and an IAM user?What is the difference between an IAM role and an IAM user?Mi a különbség egy IAM role és egy IAM user között?

  • A user is a permanent identity with long-lived access keys. A role is an identity assumed temporarily, handing out short-lived credentials — no stored keys to leak. Use roles for workloads (a service, an instance, a pipeline) and federation for humans; users with keys are the legacy path and the source of most credential leaks.A user is a permanent identity with long-lived access keys. A role is taken on for a short time and gives out short-lived credentials — there are no stored keys that could leak. Use roles for workloads (a service, an instance, a pipeline), and use federation for people. Users with keys are the old way, and they are where most credential leaks come from.Egy user állandó identitás, hosszú életű access key-ekkel. Egy role-t átmenetileg vesz fel valaki (assume), és rövid életű credentialt ad — nincs eltárolt kulcs, ami kiszivároghatna. Workloadokhoz (service, instance, pipeline) role-t használj, emberekhez federationt; a kulcsos user a régi megközelítés, és a legtöbb credential-szivárgás forrása.

How do IAM policies get evaluated?How does AWS decide what an IAM policy allows?Hogyan értékelődnek ki az IAM policy-k?

  • Default deny. An explicit allow grants access; an explicit deny anywhere overrides everything. Within one account, identity-based and resource-based policies combine (union); permission boundaries and SCPs can only restrict the result. So: granted by identity or resource, capped by boundaries/SCPs, killed by any explicit deny.Everything is denied by default. An explicit allow grants access. An explicit deny anywhere beats everything else. Inside one account, identity policies and resource policies add up together. Permission boundaries and SCPs can only take access away, never add it. So: identity or resource grants it, boundaries and SCPs cap it, and any explicit deny kills it.Alapból minden tiltva van (default deny). Egy explicit allow ad hozzáférést; egy explicit deny bárhol felülír mindent. Egy accounton belül az identity-alapú és resource-alapú policy-k összeadódnak (unió); a permission boundary és az SCP csak szűkíteni tud, hozzáadni soha. Tehát: identity vagy resource megadja, a boundary/SCP korlátozza, és bármely explicit deny megöli.

What's the shared responsibility model?What is the shared responsibility model?Mi a shared responsibility model?

  • AWS secures the cloud (hardware, data centres, managed-service internals); you secure what's in it (IAM, data encryption, network config, and on EC2 the OS patching). The line moves with the service — on Fargate/Lambda AWS patches the runtime, on EC2 you do. Most breaches happen on the customer's side of this line.AWS secures the cloud itself: hardware, data centres, and the inside of managed services. You secure what you put in it: IAM, data encryption, network config, and — on EC2 — patching the OS. The line moves depending on the service: on Fargate and Lambda, AWS patches the runtime; on EC2, you do. Most breaches happen on the customer's side of this line.Az AWS a felhőt magát védi (hardver, adatközpontok, a managed service-ek belseje); te azt véded, amit beleteszel (IAM, adattitkosítás, hálózati konfiguráció, EC2-n az OS patchelése). A határ a szolgáltatástól függ: Fargate/Lambda esetén az AWS patcheli a runtime-ot, EC2-n te. A legtöbb incidens az ügyfél oldalán történik ezen a határon.

How do you store secrets in an AWS application?Where do you store secrets in an AWS application?Hogyan tárolsz secreteket egy AWS-alkalmazásban?

  • In Secrets Manager or Parameter Store — never in code or committed env files. Secrets Manager adds automatic rotation. The app fetches the secret at runtime via its IAM role, so it's never stored alongside the app. Encryption at rest is via KMS.In Secrets Manager or Parameter Store — never in code and never in committed env files. Secrets Manager can also rotate them for you. The app reads the secret at runtime using its IAM role, so the secret is never stored next to the app. It is encrypted at rest with KMS.Secrets Managerben vagy Parameter Store-ban — soha nem a kódban vagy commitolt env fájlban. A Secrets Manager ráadásul automatikusan rotálni is tudja őket. Az app futásidőben, a saját IAM role-jával olvassa ki a secretet, így az sosem az app mellett tárolódik. A nyugalmi titkosítás KMS-sel történik.

EC2, containers, or Lambda — how do you choose?EC2, containers, or Lambda — how do you choose?EC2, konténerek, vagy Lambda — hogyan választasz?

  • A spectrum of how much you manage. EC2 = full control (legacy, special hardware). Containers (ECS/EKS) = portable, standard for most services. Lambda = event-driven and spiky, scales to zero. Match to the workload: steady high traffic favours containers, spiky event work favours Lambda, deep control needs favour EC2.It is a range of how much you manage. EC2 = full control (good for legacy apps or special hardware). Containers (ECS/EKS) = portable and the standard choice for most services. Lambda = event-driven and spiky, and it can scale down to zero. Match it to the workload: steady high traffic fits containers, spiky event work fits Lambda, and a need for deep control fits EC2.Egy skála arról, mennyit kell kezelned. EC2 = teljes kontroll (legacy appokhoz vagy speciális hardverhez). Konténerek (ECS/EKS) = hordozható, és a legtöbb service-hez ez az alap választás. Lambda = event-driven és hullámzó terhelésű, akár nullára is leskálázódik. Igazítsd a workloadhoz: az egyenletes, nagy forgalomhoz konténer, a hullámzó event-alapú munkához Lambda, a mély kontrollhoz EC2 illik.

ECS or EKS?ECS or EKS?ECS vagy EKS?

  • ECS is simpler and AWS-native — less to operate. EKS is managed Kubernetes — portable, huge ecosystem, but more operational weight. Choose EKS if you need k8s portability or the team already knows it; otherwise ECS (with Fargate) is often the more defensible call. Don't pick EKS just for its own sake.ECS is simpler and AWS-native, so there is less to run. EKS is managed Kubernetes: portable, with a huge ecosystem, but it takes more work to operate. Choose EKS if you need Kubernetes portability, or if the team already knows it. Otherwise ECS (with Fargate) is often the safer choice. Do not pick EKS just because it is popular.Az ECS egyszerűbb és AWS-natív — kevesebb az üzemeltetni való. Az EKS managed Kubernetes: hordozható, hatalmas ökoszisztémával, de több üzemeltetési teherrel. EKS-t akkor válassz, ha Kubernetes-hordozhatóság kell, vagy a csapat már ismeri; egyébként az ECS (Fargate-tel) sokszor a védhetőbb döntés. Ne az EKS-t válaszd csak azért, mert népszerű.

What's a Lambda cold start?What is a Lambda cold start?Mi az a Lambda cold start?

  • The first invocation of an idle function pays initialisation time (runtime spins up, init code runs), adding latency a warm invocation doesn't. It bites latency-sensitive paths. Mitigate with provisioned concurrency (keeps instances warm, at a cost) or a lighter runtime — or use a container for a synchronous API with tight latency needs.When an idle function runs for the first time, it pays start-up time: the runtime boots and the init code runs. This adds delay that a warm call does not have. It hurts latency-sensitive paths. You can reduce it with provisioned concurrency (keeps instances warm, but costs money) or a lighter runtime — or use a container for a synchronous API that needs low latency.Amikor egy tétlen (idle) function először fut le, megfizeti az indulási időt: felpörög a runtime és lefut az init kód. Ez késleltetést ad, amit egy warm hívásnál nem kapsz meg. A latency-érzékeny utakon fáj. Csökkentheted provisioned concurrency-vel (melegen tartja az instance-okat, de pénzbe kerül) vagy könnyebb runtime-mal — vagy használj konténert egy alacsony késleltetést igénylő szinkron API-hoz.

How does auto scaling work, and what's the risk?How does auto scaling work, and what is the risk?Hogyan működik az auto scaling, és mi a kockázata?

  • An Auto Scaling Group adds/removes instances behind a load balancer based on a metric (CPU, request count) or schedule, giving elastic, self-healing capacity. The risk: without a maximum cap, a traffic spike or runaway bug can scale you into a huge bill. Always set a max and alert on hitting it.An Auto Scaling Group adds or removes instances behind a load balancer, based on a metric (CPU, request count) or a schedule. This gives you elastic, self-healing capacity. The risk: with no maximum limit, a traffic spike or a runaway bug can scale up into a huge bill. Always set a maximum and alert when you hit it.Egy Auto Scaling Group instance-okat ad hozzá vagy vesz el egy load balancer mögött, egy metrika (CPU, kérésszám) vagy időzítés alapján. Ez rugalmas, önjavító kapacitást ad. A kockázat: felső korlát nélkül egy forgalmi tüske vagy egy elszabadult bug hatalmas számlára tud felskálázni. Mindig állíts be maximumot, és riasztást, ha eléred.

When do you use S3 vs EBS vs EFS?When do you use S3 vs EBS vs EFS?Mikor használsz S3-at vs EBS-t vs EFS-t?

  • S3 = object storage over HTTP (files, backups, static sites, data lakes). EBS = a disk for a single instance (OS disk, databases). EFS = a shared filesystem many instances mount at once. Shorthand: files-over-HTTP → S3, one instance's disk → EBS, many writers one filesystem → EFS.S3 = object storage over HTTP (files, backups, static sites, data lakes). EBS = a disk for a single instance (the OS disk, databases). EFS = a shared filesystem that many instances mount at the same time. Short version: files over HTTP → S3, one instance's disk → EBS, many writers on one filesystem → EFS.S3 = object storage HTTP-n (fájlok, backupok, statikus oldalak, data lake-ek). EBS = lemez egyetlen instance-nak (OS-lemez, adatbázisok). EFS = megosztott fájlrendszer, amit sok instance mountol egyszerre. Röviden: fájlok HTTP-n → S3, egy instance lemeze → EBS, sok író egy fájlrendszeren → EFS.

RDS or DynamoDB?RDS or DynamoDB?RDS vagy DynamoDB?

  • Down to the access pattern. Relational data with flexible, ad-hoc queries → RDS/Aurora. Massive scale with known, simple key-based access → DynamoDB. DynamoDB forces you to model tables around your queries, so "we don't know the access patterns yet" points to relational.It comes down to the access pattern. Relational data with flexible, ad-hoc queries → RDS/Aurora. Very large scale with known, simple key-based access → DynamoDB. DynamoDB makes you design tables around your queries, so "we do not know the access patterns yet" points to relational.Az access patternen múlik. Relációs adat rugalmas, ad-hoc query-kkel → RDS/Aurora. Nagyon nagy skála ismert, egyszerű, kulcs-alapú eléréssel → DynamoDB. A DynamoDB-nél a query-k köré kell tervezned a táblákat, tehát a „még nem tudjuk az access patterneket" a relációs felé mutat.

How do you scale reads on a relational database?How do you scale reads on a relational database?Hogyan skálázod az olvasásokat egy relációs adatbázison?

Read replicas take read load off the primary; a cache absorbs hot reads before they hit the DB at all. Start cheap and simple, escalate only as needed.Go in this order: tune queries and add indexes → add a cache (ElastiCache) → add read replicas → scale up the instance → shard last. Read replicas take read load off the primary. A cache serves hot reads before they reach the database at all. Start cheap and simple, and only move up the list when you need to.Ebben a sorrendben: query-hangolás és indexek → cache (ElastiCache) → read replica-k → nagyobb instance (vertical scaling) → sharding legvégső esetben. A read replica leveszi az olvasási terhelést a primaryről; a cache kiszolgálja a gyakori olvasásokat, mielőtt egyáltalán elérnék az adatbázist. Kezdd az olcsó, egyszerű lépéssel, és csak akkor lépj feljebb, ha muszáj.

Is a read replica a backup?Is a read replica a backup?Egy read replica az backupnak számít?

  • No — three different features solve three problems. Read replicas serve read traffic; a Multi-AZ standby handles failover (availability); snapshots and point-in-time recovery are the backup (durability). Conflating them ("it's replicated so it's backed up") is a common slip — replication is availability, backup is durability.No. Three different features solve three different problems. Read replicas serve read traffic. A Multi-AZ standby handles failover (availability). Snapshots and point-in-time recovery are the backup (durability). Mixing these up ("it is replicated, so it is backed up") is a common mistake — replication is about availability, backup is about durability.Nem. Három külön feature három külön problémát old meg. A read replica olvasási forgalmat szolgál ki; egy Multi-AZ standby a failovert (availability) kezeli; a snapshot és a point-in-time recovery a backup (durability). Ezek összekeverése („replikálva van, tehát mentve van") gyakori hiba — a replikáció az availability-ről szól, a backup a durability-ről.

What's the difference between Multi-AZ and multi-region?What is the difference between Multi-AZ and multi-region?Mi a különbség a Multi-AZ és a multi-region között?

  • Multi-AZ = spreading across Availability Zones within one region, to survive a data-centre (AZ) failure — the default for production, cheap. Multi-region = running across regions, to survive a whole-region outage — rare, expensive, with data-consistency complexity. Multi-AZ is the baseline; multi-region is the exception you justify with strict requirements.Multi-AZ = spreading across Availability Zones inside one region, to survive a data-centre (AZ) failure. It is the default for production and it is cheap. Multi-region = running across regions, to survive a whole-region outage. It is rare, expensive, and adds data-consistency problems. Multi-AZ is the baseline; multi-region is the exception you justify with strict requirements.Multi-AZ = szétterítés Availability Zone-ok között egy régión belül, hogy túléld egy adatközpont (AZ) kiesését — ez a production alapértelmezés, és olcsó. Multi-region = több régióban futtatás, hogy túléld egy egész régió kiesését — ritka, drága, és data-consistency problémákat hoz. A Multi-AZ az alap; a multi-region a kivétel, amit szigorú követelményekkel indokolsz.

What's the difference between RTO and RPO?What is the difference between RTO and RPO?Mi a különbség az RTO és az RPO között?

  • RTO (Recovery Time Objective) = how long you can be down — the downtime window. RPO (Recovery Point Objective) = how much data you can lose — the data-loss window, set by backup frequency. A daily backup means an RPO of up to 24 hours regardless of how fast your RTO is. They're independent numbers.RTO (Recovery Time Objective) = how long you can be down — the downtime window. RPO (Recovery Point Objective) = how much data you can lose — the data-loss window, which your backup frequency sets. A daily backup means an RPO of up to 24 hours, no matter how fast your RTO is. They are two separate numbers.RTO (Recovery Time Objective) = meddig lehetsz leállva — a downtime-ablak. RPO (Recovery Point Objective) = mennyi adatot veszíthetsz — az adatvesztési ablak, amit a backup gyakorisága határoz meg. Egy napi backup akár 24 órás RPO-t jelent, függetlenül attól, milyen gyors az RTO-d. Ez két különálló szám.

What's the difference between availability and durability?What is the difference between availability and durability?Mi a különbség az availability és a durability között?

  • Durability = your data survives (S3 essentially never loses an object). Availability = you can reach it right now (Multi-AZ failover keeps it reachable). Different problems solved by different features — you often need both, and confusing them leads to gaps.Durability = your data survives (S3 almost never loses an object). Availability = you can reach it right now (Multi-AZ failover keeps it reachable). These are different problems, solved by different features. You often need both, and mixing them up leaves gaps.Durability = az adatod megmarad (az S3 gyakorlatilag sosem veszít el objektumot). Availability = épp most is eléred (a Multi-AZ failover elérhetően tartja). Ez két külön probléma, külön feature-ökkel megoldva — sokszor mindkettő kell, és az összekeverésük réseket hagy.

How do you pick a DR strategy?How do you pick a DR strategy?Hogyan választasz DR-stratégiát?

  • Let the RTO/RPO decide. Backup & Restore (cheapest, hours of downtime) → Pilot Light (core running) → Warm Standby (scaled-down live copy) → Active-Active (multi-region, near-zero RTO, priciest). Ask "how long can this be down and how much data can we lose?" then match the cheapest strategy that meets it. And test it — an untested DR plan is a hypothesis.Let the RTO/RPO decide. Backup & Restore (cheapest, hours of downtime) → Pilot Light (core parts running) → Warm Standby (a smaller live copy) → Active-Active (multi-region, almost no downtime, most expensive). Ask "how long can this be down, and how much data can we lose?" then pick the cheapest strategy that meets it. And test it — a DR plan you have never tested is only a guess.Hagyd, hogy az RTO/RPO döntsön. Backup & Restore (legolcsóbb, órákban mért downtime) → Pilot Light (a mag fut) → Warm Standby (kicsinyített élő másolat) → Active-Active (multi-region, közel nulla downtime, legdrágább). Kérdezd meg: „meddig lehet ez leállva, és mennyi adatot veszíthetünk?", majd válaszd a legolcsóbb stratégiát, ami ezt teljesíti. És teszteld — egy sosem tesztelt DR-terv csak feltételezés.

A választás illeszkedés kérdése — meglévő tooling, csapat-tudás, multi-cloud igény —, nem csak hordozhatóságé. Ismerd a trade-offot, ne dogmatikusan preferáld az egyiket.

Why does Terraform state matter so much?Why does Terraform state matter so much?Miért olyan fontos a Terraform state?

What's the difference between RAG and fine-tuning?What is the difference between RAG and fine-tuning?Mi a különbség a RAG és a fine-tuning között?

  • RAG injects your data at query time — retrieve relevant chunks, put them in the prompt — so knowledge stays current (update documents, not the model), citeable, and access-controllable per user. Fine-tuning bakes knowledge into the weights: expensive, static, for changing the model's behaviour or style, not for feeding it facts. For a knowledge base, RAG is almost always the right first answer.RAG adds your data at query time — it fetches the relevant chunks and puts them in the prompt.
