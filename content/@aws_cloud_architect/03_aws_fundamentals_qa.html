Networking QuestionsHálózati kérdések

What's the difference between a security group and a NACL?Mi a különbség egy security group és egy NACL között?

  • Security group: stateful, attached to a resource (instance-level), allow rules only, return traffic automatic. NACL: stateless, attached to a subnet, allow and deny rules, each direction evaluated independently (so you must allow the return ephemeral ports). In practice SGs do the real work; NACLs are a coarse subnet backstop.Security group: állapottartó, egy erőforráshoz kapcsolva (instance-szintű), csak allow szabályok, a visszatérő forgalom automatikus. NACL: állapotmentes, egy subnethez kapcsolva, allow és deny szabályok, minden irány függetlenül értékelve (tehát engedélyezned kell a visszatérő ephemeral portokat). A gyakorlatban az SG-k végzik a valódi munkát; a NACL-ök durva subnet-tartalék.

What makes a subnet "public"?Mitől lesz egy subnet „publikus"?

  • A route in its route table pointing 0.0.0.0/0 to an Internet Gateway. That's the only thing — a "private" subnet simply lacks that route and reaches the internet (if at all) via a NAT gateway instead.Egy útvonal a route table-jében, ami a 0.0.0.0/0-t egy Internet Gateway-re mutatja. Ez az egyetlen dolog — egy „privát" subnetnek egyszerűen nincs ilyen útvonala, és (ha egyáltalán) egy NAT gateway-en át éri el az internetet.

How does a private instance download OS updates?Hogyan tölt le egy privát instance OS-frissítéseket?

  • Through a NAT gateway in a public subnet — it lets private resources make outbound connections while staying unreachable from the internet. For AWS services specifically (like S3), a VPC endpoint is better: it avoids NAT cost and keeps traffic off the public internet.Egy publikus subnetben lévő NAT gateway-en át — ez hagyja a privát erőforrásokat kimenő kapcsolatokat létesíteni, míg elérhetetlenek maradnak az internetről. Kifejezetten AWS-szolgáltatásokhoz (mint az S3) egy VPC endpoint jobb: elkerüli a NAT-költséget és távol tartja a forgalmat a nyilvános internettől.

When would you use a VPC endpoint?Mikor használnál VPC endpointot?

  • To reach an AWS service privately without traffic leaving the AWS network. A gateway endpoint (S3, DynamoDB) is free and removes NAT cost for that traffic; an interface endpoint (PrivateLink) covers other services. Canonical use: reaching S3 from a private subnet without a NAT gateway.Egy AWS szolgáltatás privát elérésére úgy, hogy a forgalom nem hagyja el az AWS hálózatot. Egy gateway endpoint (S3, DynamoDB) ingyenes és megszünteti a NAT-költséget arra a forgalomra; egy interface endpoint (PrivateLink) a többi szolgáltatást fedi. Kanonikus használat: S3 elérése egy privát subnetből NAT gateway nélkül.

IAM & Security QuestionsIAM & biztonsági kérdések

What's the difference between an IAM role and an IAM user?Mi a különbség egy IAM role és egy IAM user között?

  • A user is a permanent identity with long-lived access keys. A role is an identity assumed temporarily, handing out short-lived credentials — no stored keys to leak. Use roles for workloads (a service, an instance, a pipeline) and federation for humans; users with keys are the legacy path and the source of most credential leaks.Egy user egy állandó identitás hosszú életű access key-ekkel. Egy role egy ideiglenesen felvett identitás, amely rövid életű hitelesítő adatokat oszt — nincs tárolt kulcs, ami kiszivároghatna. Használj role-okat workloadokhoz (egy szolgáltatás, egy instance, egy pipeline) és föderációt embereknek; a kulcsos userek a legacy út és a legtöbb credential-szivárgás forrása.

How do IAM policies get evaluated?Hogyan értékelődnek ki az IAM policy-k?

  • Default deny. An explicit allow grants access; an explicit deny anywhere overrides everything. Within one account, identity-based and resource-based policies combine (union); permission boundaries and SCPs can only restrict the result. So: granted by identity or resource, capped by boundaries/SCPs, killed by any explicit deny.Alapból deny. Egy explicit allow ad hozzáférést; egy explicit deny bárhol mindent felülír. Egy accounton belül az identity- és resource-alapú policy-k kombinálódnak (unió); a permission boundary-k és SCP-k csak korlátozhatják az eredményt. Tehát: identity vagy resource ad, boundary-k/SCP-k korlátoznak, bármely explicit deny megöl.

What's the shared responsibility model?Mi a megosztott felelősség modell?

  • AWS secures the cloud (hardware, data centres, managed-service internals); you secure what's in it (IAM, data encryption, network config, and on EC2 the OS patching). The line moves with the service — on Fargate/Lambda AWS patches the runtime, on EC2 you do. Most breaches happen on the customer's side of this line.Az AWS a felhőt biztosítja (hardver, adatközpontok, menedzselt-szolgáltatás belsők); te azt, ami benne van (IAM, adattitkosítás, hálózati konfig, és EC2-n az OS-patchelés). A vonal a szolgáltatással mozog — Fargate/Lambdán az AWS patcheli a futtatókörnyezetet, EC2-n te. A legtöbb betörés a vonal ügyfél-oldalán történik.

How do you store secrets in an AWS application?Hogyan tárolsz titkokat egy AWS-alkalmazásban?

  • In Secrets Manager or Parameter Store — never in code or committed env files. Secrets Manager adds automatic rotation. The app fetches the secret at runtime via its IAM role, so it's never stored alongside the app. Encryption at rest is via KMS.Secrets Managerben vagy Parameter Store-ban — soha nem kódban vagy commitolt env-fájlokban. A Secrets Manager automatikus rotációt ad. Az app futásidőben kéri le a titkot az IAM role-ján át, így sosem tárolódik az app mellett. A nyugalmi titkosítás KMS-en át.

Compute QuestionsSzámítási kérdések

EC2, containers, or Lambda — how do you choose?EC2, konténerek, vagy Lambda — hogyan választasz?

  • A spectrum of how much you manage. EC2 = full control (legacy, special hardware). Containers (ECS/EKS) = portable, standard for most services. Lambda = event-driven and spiky, scales to zero. Match to the workload: steady high traffic favours containers, spiky event work favours Lambda, deep control needs favour EC2.Egy spektrum arról, mennyit kezelsz. EC2 = teljes kontroll (legacy, speciális hardver). Konténerek (ECS/EKS) = hordozható, standard a legtöbb szolgáltatáshoz. Lambda = eseményvezérelt és csúcsos, nullára skálázódik. Illeszd a workloadhoz: az állandó nagy forgalom konténereket preferál, a csúcsos esemény-munka Lambdát, a mély kontroll-igény EC2-t.

ECS or EKS?ECS vagy EKS?

  • ECS is simpler and AWS-native — less to operate. EKS is managed Kubernetes — portable, huge ecosystem, but more operational weight. Choose EKS if you need k8s portability or the team already knows it; otherwise ECS (with Fargate) is often the more defensible call. Don't pick EKS just for its own sake.Az ECS egyszerűbb és AWS-natív — kevesebb üzemeltetés. Az EKS menedzselt Kubernetes — hordozható, hatalmas ökoszisztéma, de több üzemeltetési súly. Válaszd az EKS-t, ha k8s-hordozhatóság kell vagy a csapat már ismeri; egyébként az ECS (Fargate-tel) gyakran a védhetőbb döntés. Ne válaszd az EKS-t önmagáért.

What's a Lambda cold start?Mi egy Lambda hidegindítás?

  • The first invocation of an idle function pays initialisation time (runtime spins up, init code runs), adding latency a warm invocation doesn't. It bites latency-sensitive paths. Mitigate with provisioned concurrency (keeps instances warm, at a cost) or a lighter runtime — or use a container for a synchronous API with tight latency needs.Egy tétlen függvény első meghívása inicializálási időt fizet (a futtatókörnyezet felpörög, az init-kód lefut), késleltetést adva, amit egy meleg meghívás nem. Késleltetés-érzékeny utakon üt. Provisioned concurrency-vel enyhítsd (melegen tartja az instance-okat, költséggel) vagy könnyebb futtatókörnyezettel — vagy használj konténert egy szinkron, szoros késleltetésű API-hoz.

How does auto scaling work, and what's the risk?Hogyan működik az auto scaling, és mi a kockázat?

  • An Auto Scaling Group adds/removes instances behind a load balancer based on a metric (CPU, request count) or schedule, giving elastic, self-healing capacity. The risk: without a maximum cap, a traffic spike or runaway bug can scale you into a huge bill. Always set a max and alert on hitting it.Egy Auto Scaling Group instance-okat ad/vesz egy load balancer mögött egy metrika (CPU, kérésszám) vagy ütemezés alapján, elasztikus, öngyógyító kapacitást adva. A kockázat: felső korlát nélkül egy forgalmi csúcs vagy elszabadult hiba hatalmas számlára skálázhat. Mindig állíts maximumot és riassz a beütésére.

Storage & Database QuestionsTárolási & adatbázis kérdések

When do you use S3 vs EBS vs EFS?Mikor használsz S3-at vs EBS-t vs EFS-t?

  • S3 = object storage over HTTP (files, backups, static sites, data lakes). EBS = a disk for a single instance (OS disk, databases). EFS = a shared filesystem many instances mount at once. Shorthand: files-over-HTTP → S3, one instance's disk → EBS, many writers one filesystem → EFS.S3 = objektum-tárolás HTTP-n (fájlok, mentések, statikus oldalak, data lake-ek). EBS = lemez egyetlen instance-nak (OS-lemez, adatbázisok). EFS = megosztott fájlrendszer, amit sok instance mountol egyszerre. Röviden: fájlok-HTTP-n → S3, egy instance lemeze → EBS, sok író egy fájlrendszer → EFS.

RDS or DynamoDB?RDS vagy DynamoDB?

  • Down to the access pattern. Relational data with flexible, ad-hoc queries → RDS/Aurora. Massive scale with known, simple key-based access → DynamoDB. DynamoDB forces you to model tables around your queries, so "we don't know the access patterns yet" points to relational.A hozzáférési mintán múlik. Relációs adat rugalmas, ad-hoc lekérdezésekkel → RDS/Aurora. Hatalmas lépték ismert, egyszerű kulcs-alapú hozzáféréssel → DynamoDB. A DynamoDB arra kényszerít, hogy a táblákat a lekérdezéseid köré modellezd, tehát a „még nem tudjuk a hozzáférési mintákat" a relációsra mutat.

How do you scale reads on a relational database?Hogyan skálázod az olvasásokat egy relációs adatbázison?

  • Escalation order: query tuning and indexes → a cache (ElastiCache) → read replicas → vertical scaling → sharding last. Read replicas take read load off the primary; a cache absorbs hot reads before they hit the DB at all. Start cheap and simple, escalate only as needed.Eszkalációs sorrend: lekérdezés-hangolás és indexek → egy cache (ElastiCache) → olvasó replikák → függőleges skálázás → shardolás utoljára. Az olvasó replikák leveszik az olvasási terhelést a primaryről; egy cache felszívja a forró olvasásokat, mielőtt egyáltalán elérnék az adatbázist. Kezdd olcsón és egyszerűen, eszkalálj csak szükség szerint.

Is a read replica a backup?Egy olvasó replika mentés?

  • No — three different features solve three problems. Read replicas serve read traffic; a Multi-AZ standby handles failover (availability); snapshots and point-in-time recovery are the backup (durability). Conflating them ("it's replicated so it's backed up") is a common slip — replication is availability, backup is durability.Nem — három különböző funkció három problémát old meg. Az olvasó replikák olvasási forgalmat szolgálnak ki; egy Multi-AZ standby kezeli a failovert (rendelkezésre állás); a snapshotok és a point-in-time recovery a mentés (tartósság). Az összemosásuk („replikált, tehát mentve van") gyakori botlás — a replikáció rendelkezésre állás, a mentés tartósság.

Availability & DR QuestionsRendelkezésre állás & DR kérdések

What's the difference between Multi-AZ and multi-region?Mi a különbség a Multi-AZ és a multi-region között?

  • Multi-AZ = spreading across Availability Zones within one region, to survive a data-centre (AZ) failure — the default for production, cheap. Multi-region = running across regions, to survive a whole-region outage — rare, expensive, with data-consistency complexity. Multi-AZ is the baseline; multi-region is the exception you justify with strict requirements.Multi-AZ = szétosztás Availability Zone-ok között egy régión belül, hogy túléld egy adatközpont (AZ) hibáját — a produkciós alapértelmezés, olcsó. Multi-region = régiók közti futtatás, hogy túléld egy teljes régió kiesését — ritka, drága, adatkonzisztencia-bonyolultsággal. A Multi-AZ az alapvonal; a multi-region a kivétel, amit szigorú követelményekkel indokolsz.

What's the difference between RTO and RPO?Mi a különbség az RTO és az RPO között?

  • RTO (Recovery Time Objective) = how long you can be down — the downtime window. RPO (Recovery Point Objective) = how much data you can lose — the data-loss window, set by backup frequency. A daily backup means an RPO of up to 24 hours regardless of how fast your RTO is. They're independent numbers.RTO (Recovery Time Objective) = meddig lehetsz leállva — a leállási ablak. RPO (Recovery Point Objective) = mennyi adatot veszíthetsz — az adatvesztési ablak, a mentés gyakorisága állítja. Egy napi mentés akár 24 órás RPO-t jelent, függetlenül attól, milyen gyors az RTO-d. Ezek független számok.

What's the difference between availability and durability?Mi a különbség rendelkezésre állás és tartósság között?

  • Durability = your data survives (S3 essentially never loses an object). Availability = you can reach it right now (Multi-AZ failover keeps it reachable). Different problems solved by different features — you often need both, and confusing them leads to gaps.Tartósság = az adatod túléli (az S3 lényegében sosem veszít objektumot). Rendelkezésre állás = most el tudod érni (a Multi-AZ failover elérhetően tartja). Különböző problémák, különböző funkciókkal megoldva — gyakran mindkettő kell, és az összekeverésük hiányokhoz vezet.

How do you pick a DR strategy?Hogyan választasz DR-stratégiát?

  • Let the RTO/RPO decide. Backup & Restore (cheapest, hours of downtime) → Pilot Light (core running) → Warm Standby (scaled-down live copy) → Active-Active (multi-region, near-zero RTO, priciest). Ask "how long can this be down and how much data can we lose?" then match the cheapest strategy that meets it. And test it — an untested DR plan is a hypothesis.Hagyd, hogy az RTO/RPO döntsön. Backup & Restore (legolcsóbb, órák leállás) → Pilot Light (mag fut) → Warm Standby (kicsinyített élő másolat) → Active-Active (multi-region, közel nulla RTO, legdrágább). Kérdezd: „meddig lehet ez leállva és mennyi adatot veszíthetünk?" majd illeszd a legolcsóbb megfelelő stratégiát. És teszteld — egy nem tesztelt DR-terv egy hipotézis.

IaC, CI/CD & Cost QuestionsIaC, CI/CD & költség kérdések

Terraform or CloudFormation?Terraform vagy CloudFormation?

  • CloudFormation is AWS-native and AWS manages the stack state; Terraform is cloud-agnostic, the market standard, but needs explicit remote-state design. The choice is org and lifecycle fit — existing tooling, team skills, multi-cloud needs — not just portability. Know the trade-off rather than dogmatically preferring one.A CloudFormation AWS-natív és az AWS kezeli a stack state-et; a Terraform felhő-agnosztikus, a piaci standard, de explicit remote-state tervezést igényel. A választás org- és életciklus-illeszkedés — meglévő eszközök, csapat-készségek, multi-cloud igények — nem csak hordozhatóság. Ismerd a trade-offot, ne preferáld dogmatikusan az egyiket.

Why does Terraform state matter so much?Miért számít ennyire a Terraform state?

  • It's Terraform's record of what it manages, and it breaks at team scale if mishandled. Store it in an encrypted, versioned S3 bucket with native locking (use_lockfile; the old DynamoDB lock table is deprecated), separated per environment. It holds secrets in plaintext, so lock down access. Concurrent applies without locking corrupt it.Ez a Terraform feljegyzése arról, mit kezel, és csapat-léptékben eltörik, ha rosszul kezelik. Tárold titkosított, verziózott S3 bucketben natív lockinggal (use_lockfile; a régi DynamoDB lock-tábla deprecated), környezetenként elkülönítve. Titkokat tart sima szövegben, tehát zárd le a hozzáférést. A locking nélküli párhuzamos apply-ok megrongálják.

How should a CI/CD pipeline authenticate to AWS?Hogyan autentikáljon egy CI/CD pipeline az AWS felé?

  • With OIDC federation, not stored access keys. The pipeline presents a short-lived OIDC token that AWS exchanges for temporary role credentials — no long-lived secret in CI to leak. This is current best practice; storing an access key as a CI secret is the old, riskier way.OIDC föderációval, nem tárolt access key-ekkel. A pipeline egy rövid életű OIDC tokent mutat be, amit az AWS ideiglenes role-hitelesítő adatokra vált — nincs hosszú életű titok a CI-ban, ami kiszivároghatna. Ez a jelenlegi best practice; egy access key CI-titokként tárolása a régi, kockázatosabb mód.

Where do the big AWS cost savings usually hide?Hol rejtőznek általában a nagy AWS-költségmegtakarítások?

  • In data transfer (NAT gateway processing, cross-AZ and cross-region traffic, internet egress) and over-provisioning (oversized instances, dev environments left running, idle resources). Architectural fixes — VPC endpoints, right-sizing, scale-to-zero — beat hunting pennies. Plus commitment discounts (Savings Plans/Reserved) for steady load and Spot for interruptible work.Az adatátvitelben (NAT gateway feldolgozás, cross-AZ és cross-region forgalom, internet-kimenet) és a túlméretezésben (túl nagy instance-ok, futva hagyott dev-környezetek, tétlen erőforrások). Az architekturális javítások — VPC endpointok, right-sizing, nullára skálázás — verik a fillérvadászatot. Plusz elköteleződési kedvezmények (Savings Plan/Reserved) állandó terheléshez és Spot a megszakítható munkához.

GenAI QuestionsGenAI kérdések

What's the difference between RAG and fine-tuning?Mi a különbség a RAG és a fine-tuning között?

  • RAG injects your data at query time — retrieve relevant chunks, put them in the prompt — so knowledge stays current (update documents, not the model), citeable, and access-controllable per user. Fine-tuning bakes knowledge into the weights: expensive, static, for changing the model's behaviour or style, not for feeding it facts. For a knowledge base, RAG is almost always the right first answer.A RAG lekérdezéskor injektálja az adatodat — releváns darabok lekérése, promptba tétele — így a tudás aktuális marad (a dokumentumokat frissíted, nem a modellt), idézhető, és felhasználónként hozzáférés-szabályozható. A fine-tuning a súlyokba süti a tudást: drága, statikus, a modell viselkedésének vagy stílusának megváltoztatására, nem tények betáplálására. Egy tudásbázishoz a RAG szinte mindig a helyes első válasz.

Why use Bedrock instead of self-hosting a model?Miért Bedrock egy modell self-hostingja helyett?

  • Managed access to foundation models through one API — no GPU fleet to run, with AWS identity, encryption, and network controls, reachable privately via PrivateLink. Model providers don't get your account or prompts. The model doesn't run in your VPC, so verify data handling for sensitive workloads. Self-host (SageMaker) only for full control or a specific fine-tuned model.Menedzselt hozzáférés alapmodellekhez egy API-n át — nincs futtatandó GPU-flotta, AWS identitással, titkosítással, és hálózati kontrollokkal, privátan elérhetően PrivateLinken át. A modell-szolgáltatók nem kapják az accountodat vagy promptjaidat. A modell nem a te VPC-dben fut, tehát ellenőrizd az adatkezelést érzékeny workloadoknál. Self-host (SageMaker) csak a teljes kontrollhoz vagy egy konkrét fine-tuned modellhez.

Where does a vector database fit in a GenAI system?Hova illik egy vektoradatbázis egy GenAI-rendszerben?

  • It's the retrieval engine behind RAG: it stores embeddings (numerical representations of your document chunks) and finds the ones most similar to a query. On AWS: OpenSearch's vector engine, RDS/Aurora PostgreSQL with pgvector, or a dedicated store. A normal data-layer choice — pgvector if you already run Postgres and volume is modest, OpenSearch or dedicated when scale demands it.Ez a RAG mögötti lekérési motor: embeddingeket tárol (a dokumentumdarabjaid numerikus reprezentációit), és megtalálja a kérdéshez leghasonlóbbakat. AWS-en: az OpenSearch vektor-motorja, RDS/Aurora PostgreSQL pgvector-rel, vagy egy dedikált tároló. Egy normális adatréteg-döntés — pgvector, ha már futtatsz Postgrest és a volumen szerény, OpenSearch vagy dedikált, amikor a lépték megköveteli.
